# Performance Engineering

Performance is an observable contract only when the workload, semantics,
environment, and statistical method are reproducible. A benchmark result does
not override correctness, compatibility, durability, security, cancellation,
or resource bounds.

## Inventory

[`benchmarks.json`](../benchmarks.json) is the machine-readable inventory of
benchmark sources, documentation, retained baselines, comparison harnesses,
required services, and gate applicability. The generated
[benchmark catalog](benchmark-catalog.md) is its human-readable view. Both are
regenerated by `make manifests`; repository validation fails when either is
stale.

The catalog reports discoverable assets, not benchmark quality. A required
module with a benchmark function has executable coverage, but it still needs a
reviewed workload, representative fixtures, resource limits, and an honest
comparison disposition before performance readiness can be claimed.

## Running Benchmarks

Run one module through the same evidence-producing gate used by CI:

```bash
make benchmark MODULES=pkg/jsonrpc JOBS=1
```

The module's `Makefile` owns its benchmark command and any provider lifecycle.
Direct `go test -bench` use is useful while developing a benchmark, but it does
not replace the repository gate or its attributable evidence.

Every retained baseline must identify:

- repository content identity and owned module version;
- Go version, compiler flags, operating system, architecture, and CPU;
- `GOMAXPROCS`, GC settings, power mode, and relevant process isolation;
- dependency and service image versions;
- fixture identity, size, setup, warmup, timed region, and cleanup;
- benchmark flags, process count, sample count, and statistical method;
- raw output, failures, exclusions, and known non-equivalent behavior.

Do not combine results from different machines into one ranking. Shared CI
runners may compile harnesses and detect gross failures, but authoritative
comparisons require controlled runners and repeated process-level samples.

## Workload Design

Separate construction, compilation, cold start, warm steady state, and cleanup.
Measure small, representative, large, and adversarial inputs. Where the public
contract supports them, include sequential and concurrent use, cancellation,
failure, retry, cache miss, and degraded dependencies.

Keep fixture generation, random input creation, logging, network startup, and
service reset outside the timed region unless one is the operation under test.
Use deterministic fixtures and stable benchmark names. Report latency,
throughput, bytes and allocations per operation, and peak or steady-state RSS
where heap retention or service footprint matters.

## Comparative Fairness

Every comparison must declare one class:

1. **Raw baseline** measures abstraction overhead against a standard-library,
   native-client, direct-SQL, or smallest-correct implementation.
2. **Common denominator** exercises only behavior every candidate supports.
3. **Feature equivalent** enables matching production guarantees and output.
4. **Full owned behavior** measures the recommended Golib path without ranking
   it against less capable alternatives.
5. **Cross architecture** reports different transports, runtimes, persistence,
   or process models separately and does not present them as directly rankable.

Before ranking, a shared correctness suite must prove equivalent output,
errors, protocol semantics, state transitions, durability point, limits, and
cleanup. Setup placement, validation, serialization, synchronization, retries,
acknowledgement, TLS, transactions, and safety limits must match. Incorrect or
incomparable candidates remain visible as disqualified or separate results;
they are never silently omitted.

## Resource Limits

Performance-sensitive modules must document and exercise relevant limits for
input size, nesting, references, concurrency, queue depth, retries, cache
capacity, diagnostic output, database batches, goroutines, and retained state.
No package may create input-proportional goroutines or unbounded retained state
without an enforced limit. Benchmarks must include bounded rejection or
degradation at those limits when the behavior is operationally relevant.

## Regression Decisions

Budgets are introduced only after representative controlled measurements
exist. Use `benchstat` or an equivalent maintained statistical method over
multiple process invocations; do not gate on a single noisy shared-runner
sample or cherry-picked best result.

A statistically significant latency, throughput, allocation, memory, startup,
or binary-size regression requires investigation. A regression may be accepted
for correctness or security, but the affected module changelog and benchmark
report must record the impact, rationale, and considered alternatives. Never
weaken validation, precision, durability, cancellation, or safety to recover a
benchmark number.

## Publication

Published results must link harness source, fixtures, raw output, environment
metadata, dependency versions, capability and correctness matrices, statistics,
failures, exclusions, and limitations. Claims such as "fastest" require a
current, reproducible, scope-qualified comparison and must not conceal cases
where another implementation is faster.
